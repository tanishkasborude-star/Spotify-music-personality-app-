# SIDE A — Spotify Personality companion

An isolated Expo app for iOS, Android, and laptop/desktop browsers. It includes email/password sign-in (local demo mode by default), Spotify OAuth Authorization Code + PKCE, listening-based personality and song picks, and a compact browser dashboard widget.

## Separate package and deployments

`mobile/` is an independent npm package with its own `package.json`, `package-lock.json`, Expo config, and scripts. Run mobile commands from this directory; the root project remains the existing Vite app and its Vercel build should continue to use the repository root. Do not change the Vercel project's Root Directory or build command to point at `mobile/` to deploy the existing web app. This separation is intended to preserve the root Vite deployment; no Vercel deployment has been performed or verified as part of this starter.

The Expo web version can be hosted separately if desired, using `mobile/` as that deployment's root, `npm run export:web` as its build command, and `dist` as its output directory. This is a configuration guide, not a claim that a Vercel deployment has been tested. The compact browser widget is in-page only, not an always-on-top desktop window.

For the complete production checklist across Vercel, Expo/EAS, native widgets, Spotify, and Supabase, see the repository's [RELEASE_CHECKLIST.md](../RELEASE_CHECKLIST.md).

## Run it

```sh
cd mobile
npm install
npm run start
```

Copy `.env.example` to `.env` if you want to configure Supabase or Spotify (`Copy-Item .env.example .env` in PowerShell, or `cp .env.example .env` in a POSIX shell).

Use the terminal menu or run `npm run web`, `npm run ios`, or `npm run android`. Web runs in a normal browser, including desktop/laptop browsers. Browser layout switches to a compact two-column dashboard above 760 px; its mini-player lives inside the page and is **not always-on-top**.

Without editing `.env`, local demo sign-in is enabled (`EXPO_PUBLIC_AUTH_MODE=mock`). Enter an email and any password of at least four characters. Demo data keeps the personality/recommendations screens usable without external services.

## Configure accounts

### Supabase email/password (optional)

1. Set `EXPO_PUBLIC_AUTH_MODE=supabase`.
2. Fill in `EXPO_PUBLIC_SUPABASE_URL` and `EXPO_PUBLIC_SUPABASE_ANON_KEY`.
3. Enable email/password authentication in Supabase. Configure email confirmation as desired.

Only the public anon key belongs in the client. Use Supabase Row Level Security for any future user data tables; do not put a service-role key in the app.

### Spotify link (optional)

1. Create an app in the [Spotify Developer Dashboard](https://developer.spotify.com/dashboard).
2. Set `EXPO_PUBLIC_SPOTIFY_CLIENT_ID` (client ID only) and choose/set `EXPO_PUBLIC_SPOTIFY_REDIRECT_URI`.
3. Register the exact redirect URI in the Spotify dashboard. For a deployed browser build, set `EXPO_PUBLIC_SPOTIFY_REDIRECT_URI` to the full HTTPS URL that hosts the mobile web app (for example, `https://music-companion.example.com/`) and register that identical URL, including path and trailing slash, with Spotify. If the mobile web build is hosted on a Vercel preview or production domain, use its actual URL; do not use the existing root Vite app URL unless the mobile web build is hosted there. For native builds, the configured deep-link scheme is `spotify-personality`; use the exact URI generated by the installed native build (commonly based on `spotify-personality://`) and register it with Spotify. Do not assume a browser URL is a native callback. This app uses its configured `EXPO_PUBLIC_SPOTIFY_REDIRECT_URI` on all platforms, so use a platform-appropriate value/build configuration and verify the generated callback before release. Spotify redirect policy may change; follow its current dashboard requirements.
4. Restart Expo after changing environment variables. Sign into SIDE A first, then choose **Connect Spotify**.

If using Supabase email confirmation or recovery redirects, add the mobile web origin (for example `https://music-companion.example.com`) to the Supabase project's Authentication URL Configuration allow-list. For native callbacks, configure the matching deep-link URL as an allowed redirect when needed. The app uses Supabase email/password sign-in; configure Supabase email/password auth and project URL allow-lists before shipping.

Keep Expo's `EXPO_PUBLIC_*` settings separate from the root Vite app's `VITE_*` settings. The existing production Vercel project should keep the repository root as its Root Directory. If you choose to host the Expo web export too, create a separate deployment with `mobile/` as Root Directory and configure that deployment's own build-time environment values. Use a separate app-appropriate Spotify redirect for the Expo web URL and native deep links; do not reuse the root Vite callback automatically.

Spotify tokens use PKCE. Access and refresh tokens are stored in SecureStore on native platforms and browser storage on web; expiring access tokens are renewed automatically, including Spotify refresh-token rotation. Existing installs with a legacy access-token-only value are migrated, but that token cannot be renewed and may require reconnecting when Spotify expires it. Spotify API access and playback availability depend on Spotify's current developer-mode/app access and account policies. Recommendations are still shown using demo picks when Spotify is disconnected; linked users get a pick based on their top tracks and Spotify Search. The app intentionally does not depend on Spotify's restricted legacy Recommendations endpoint.

## Native home-screen widget

The iOS `expo-widgets` implementation and Android App Widget both show the archetype and latest recommendation with Play/Pause controls. Android uses a small native Kotlin widget provider wired through an Expo inline module and config plugin. The latest archetype and recommendation are stored in app-private widget preferences so the OS can render the widget while the app is closed; this is not a stored listening history. Android button taps open the app via its deep link, and the app requests playback of the track shown in the widget. iOS widget actions also request playback through the app. Controls are best-effort and depend on Spotify login, an active Spotify device, account eligibility (some remote playback requires Premium), and API permissions. The in-app recommendation does not depend on playback eligibility.

Widgets are **not available in Expo Go**. Build a development/native binary (for example, `npx expo prebuild` followed by a native build, or an EAS development build) and install it before testing. Widget configuration changes require a new native build. No native home-screen widget is shown in the web app; the browser mini-player is a compact in-page UI, not a desktop overlay.

## Building and distributing phone apps

Native binaries are not downloadable from this source tree until you configure, build, test, and publish them. The existing root Vercel deployment serves the web app only; use a separate EAS native build and the corresponding app-store release process for downloadable phone apps. Before a production build:

1. The selected app IDs are `com.tanishkasborude.soundprint` and the iOS widget group is `group.com.tanishkasborude.soundprint`. Register the App Group with your Apple Developer team and verify that you control and can register these identifiers; keep them stable once published.
2. Configure Spotify and Supabase production redirect/allow-list URLs, public environment variables, app icons/splash assets, privacy disclosures, and production account/data handling. Never add a Spotify client secret or Supabase service-role key to `EXPO_PUBLIC_*` variables.
3. The EAS project is linked to `@tanishkasborude-star/spotify-personality-companion` in `app.json`. Build with `npm run build:ios`, `npm run build:android`, or `npm run build:all` from `mobile/`. Native builds and widget behavior must be tested on target devices. Android builds require the Android SDK locally or a configured EAS remote build environment. An Android preview APK has been built successfully; install it and test the widget on a physical device before store submission.
4. For iOS distribution, enroll in the Apple Developer Program, configure signing and App Store Connect, satisfy Apple's privacy/review requirements, and submit/review the resulting build. For Android distribution, configure signing credentials, enroll/configure a Google Play Console developer account, satisfy Play policy/data-safety requirements, and upload/review the resulting build.

Store accounts, signing, review, and platform-specific compliance are external prerequisites; these scripts do not publish the app and do not mean it is already available for download. Native home-screen widgets require native builds; they are not desktop always-on-top widgets.

## Project map

- `src/App.tsx` — responsive authentication and music dashboard.
- `src/services/auth.ts` — mock or Supabase email/password authentication.
- `src/services/spotify.ts` — PKCE link flow, top tracks, search-based pick, and best-effort playback calls.
- `src/services/personality.ts` — local archetype and disconnected recommendation fallback.
- `src/widgets/` — iOS widget, Android widget provider/bridge, and web fallback.
- `plugins/withAndroidMusicWidget.js` — Android receiver manifest and resource setup for prebuild.
- `app.json` — Expo identifiers, deep-link scheme, and native widget config.
- `.env.example` — public client configuration placeholders; contains no credentials.

This is a front-end companion starter, not a production account-backend or guaranteed Spotify playback client. Before release, register the selected identifiers and iOS widget group with the relevant developer programs, configure production OAuth redirects, test Spotify policy and permissions, implement token revocation, and build/test both native widgets on target devices. Android widget integration compiles in the EAS preview APK but still needs physical-device verification.
